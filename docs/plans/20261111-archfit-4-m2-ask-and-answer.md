# Archfit 4, milestone 2: ask and answer

## Overview

This is the executable plan for milestone 2 of the
[Archfit 4 design](20261110-archfit-4-architecture-change-control.md). The design wins when the two disagree.
Milestone 1 has its own plan: [Archfit 4, milestone 1](20261110-archfit-4-m1-policy-rules-record.md).

Milestone 2 (design section 16) delivers, in the App: requests as issues from one line, the balance and the preview,
the passkey, "Approve and merge", recorded approvals, the re-check, expiry and drift. It delivers Action 4. It also
closes the engine items that milestone 1 left for this milestone (M1 D4, D5, D6, D11, D12) and the release of
engine 4.0.0, Action 4 and the App together (design 11.7). It is done when:

- the whole flow works on `pumba`: set up, work, ask, answer, re-check (task 32, design 15.1);
- the protection tests pass: a changed policy in a code pull request, an old approval used again, and a direct push
  of the policy (tasks 19, 20, 28).

Each `### Task N` is one pull request in one repository: `archfit`, `archfit-app` or `archfit-action`. One worker
finishes it, and a reviewer reads it in one sitting. The team executes this plan, not ralphex. Task numbers are names,
not an order: the dependencies and the wave file (`archfit-4-team/reports/a4-m2-plan-waves.md`) give the order. Every
task names the milestone 1 tasks it needs ("M1: …").

## Development approach

- One worktree, one branch, one pull request per task. Follow each repository's `AGENTS.md` or `CLAUDE.md` and the
  team's worker protocol.
- Run impact analysis before you change or delete a symbol. In archfit use GitNexus. In archfit-app and
  archfit-action use GitNexus where the repository is indexed. Otherwise list the callers (`go list`, `grep`) in the
  pull-request description. A task marked **impact first** names the symbols.
- archfit-app: new packages sit under existing prefixes (`internal/wire`, `internal/gate`, `internal/control`) and
  follow `internal/imports_test.go`: `gate` never imports `control`; `control` reaches gate data only through the
  `internal/gate` façade. Each task that needs the façade adds its own new file there (named in the task) and edits
  no other task's façade file. `internal/gate/events.go` (event dispatch) is edited by tasks 16 and 20 only.
- archfit-app: `internal/imports_test.go` changes in tasks 3 (`go.yaml.in/yaml/v3` in `wire/policy3`), 18
  (`go-webauthn` in `control/passkey`), 25 and 26. No two of them share a wave.
- archfit-app: every pull request targets the integration branch `archfit-4` (D1), never `main`. The manager merges
  `main` into `archfit-4` after each v3 hotfix.
- archfit-app: new code goes into new packages or files beside the Archfit 3 path. The Archfit 3 path is deleted in
  tasks 25 and 26, after its replacement merged. Respect `internal/imports_test.go`. Each package keeps its
  `module.md` current. Run `make all`. Storage tasks also run the Firestore emulator tests.
- archfit-action: one script set, so its tasks run one at a time. Run `bash tests/run.sh`, `shellcheck -x`, and
  `bash tests/engine-smoke.sh` where Docker is available.
- archfit: as in milestone 1 (`make test`, `make lint`, focused checks, goldens read before they are accepted).
- Every task adds tests for the behaviour it adds or changes, success and failure, and updates the documents it makes
  wrong in the words of design section 5.
- "Merge: manager" marks a contract, protection, authentication, storage or deploy change. Other tasks merge by the
  worker when CI is green and the pull request matches its task.
- Cross-repository goldens are vendored, never fetched at test time. A vendored file changes only together with its
  `SCHEMA_SOURCE` line.

## Technical Details

### Contracts: owner and pin

| Contract | Owner, file | Consumers and how they pin |
| --- | --- | --- |
| Policy schema 3 | archfit `archfit.schema.json` | App task 3 vendors it with `SCHEMA_SOURCE` |
| Result JSON v1 | archfit `archfit.result.schema.json`, goldens in `internal/model/result/testdata` | App task 4 vendors schema and goldens; the Action keeps an engine-emitted fixture, hash-pinned (tasks 10, 30) |
| The text record | archfit goldens in `internal/output/record/testdata` | App task 4 vendors them and renders byte for byte |
| Request line and issue | archfit-app `internal/wire/request` and its goldens | archfit task 6 vendors the line goldens |
| Upload envelope 2 | archfit-app `internal/wire/envelope/envelope.v2.schema.json` | archfit-action task 10 vendors it byte for byte |

A `SCHEMA_SOURCE` names the repository, the commit (the tag at release) and the SHA-256 of each vendored file. A
test fails when a vendored file and its line disagree.

### Upload envelope 2

`schema_version` `archfit.upload-envelope.v2`; `repository`; `event` (`pull_request`, `push`, `merge_group`);
`pull_request` (number, or 0); `head_sha`; `merge_base_sha`; `target_ref`; `target_sha` (the tip the policy was read
from); `policy_digest`; `run_id`; `run_attempt`; `engine_version`; `image_digest`; `platform`; `payload_digest`
(SHA-256 of the result bytes). Removed from v1: `kind`, `base_sha`, `analyzed_sha`, `integration`,
`baseline_digest`, `labels_digest`, `policy_change`. The body is the result JSON v1 bytes.

### Action 4 check run

1. Refuse an unsafe event as today. Fetch the target tip `T` (pull request: `base_ref`; push and merge group: the
   branch).
2. If `merge-base(head, T)..head` changes `.archfit.yaml`, run `archfit check --format json --base T`. The engine
   sees the local policy differ and returns `unknown` with the record that restores it.
3. Otherwise materialize `T:.archfit.yaml` from git objects and run
   `archfit check --format json --base T --policy <that file>`.
4. Upload envelope 2 with `target_sha = T`. A re-run of the latest run of the current head fetches the new `T`, so a
   policy-only change is judged by the new policy (design 10.5).

### The request line

```text
comment-line = "/archfit request" SP reason [ SP "--expires" SP date ]
cli          = "archfit request" [ " -m " shell-quoted-reason ] [ " --expires " date ]
reason       = 1 to 500 characters of one line, trimmed
date         = YYYY-MM-DD, after the App's date, at most 365 days ahead
```

- In a comment, the first line that starts with `/archfit request` is the request; other lines are ignored. Only the
  last `--expires DATE` pair is a flag; earlier text stays in the reason. One request per comment. An edited comment
  is not read again.
- The CLI opens an issue only from a `can` answer, before a pull request exists. With `check` output and no pull
  request, it says to open a pull request first (archfit-app #111). In that issue, the body has the line first and
  the reported `can` record after it in a `text` block.
- The key (archfit-app #111): `graph`, `coupling`, `layers` and a custom `deny`: rule, from, to. `cycle`: rule, from,
  to, directed (one dependency inside a cycle). `only`: rule, the module, the library. `duplication`: rule, the
  sorted module pair and the literal digest. `unowned`: `unowned <path>`. An `exception` error has no key.
- Rejections, each with one reply: no reason; a reason over 500 characters; a bad or past date; no error that asks;
  an author without permission (D21).

### The request issue

Title: `Request: <rule> <from> -> <to>` (for `duplication`: `Request: duplication <a> <-> <b>`). Body: the reason
in a `text` block, the record with its balance, "as reported" when unverified, the linked pull requests, and the
`--expires` date. Label `archfit-request`. Assignees: the owners of the target policy. The App edits the body when a
pull request joins. The issue number is the request id.

### Approval records

An **approval** is one owner action with a passkey (a reject needs none): its kind (`approve`, `approve-until`,
`reject`, `first`, `workflow`, `confirm`, `revert`), the request when there is one, the change, the owner, the
passkey credential and the time. A **proposal** is the pull request that carries approvals to the default branch:
`archfit/policy` for request answers and reverts, the onboarding pull request for `first`, the workflow pull request
for `workflow`.

| Proposal state | Meaning | Next |
| --- | --- | --- |
| `open` | The pull request holds the approvals' changes, applied in order on the current target tip. The proposal holds the ordered approvals (at most 9), its pull request, its head SHA and the expected digest. | The App merges it, or an owner merges it on GitHub: `merged`. |
| `merged` | A push whose commit is the pull request's merge commit and whose policy digest is the expected digest. The proposal is consumed (`CompareAndSwapAll` of 3 keys: the proposal, its index entry and the repository's approved digest) and records that commit. Every approval in it counts as consumed, because each records the proposal it joined, once (archfit-app #108). | None. A redelivery of that push is a no-op. |
| `void` | An approval no longer applies to a moved target (its request reopens), or an approval stayed 24 hours without a pull request. | The owner answers again. |

- An approval joins one proposal, once. The same swap pins the proposal's head SHA and expected digest (`Join`,
  archfit-app #108). A merge of a head from before the join cannot consume the new approval: its digest does not
  match.
- A moved target: the App rewrites the branch from the new tip with the same changes and recomputes the expected
  digest. Each approval keeps its change and is consumed once.
- A `confirm` changes no file: it records the current digest as approved and ends "policy changed outside the
  flow".
- Any push that changes `.archfit.yaml` and matches no open proposal is "policy changed outside the flow" (task 20).

### App keys

Under each installation tenant:

| Key | Holds |
| --- | --- |
| `v4/repo/<repo>` | The approved digest, the outside-the-flow state, the drift issue, the expiry issues |
| `v4/request/<repo>/<issue>` | One request: key, reason, numbers (verified or "as reported"), waiting pull requests, state |
| `v4/request-index/<repo>` | Open requests by request key (index) |
| `v4/approval/<repo>/<id>` | One approval |
| `v4/proposal/<repo>/<id>` | One proposal: ordered approval ids, pull request, head SHA, expected digest, state, consuming commit |
| `v4/proposal-index/<repo>` | Open proposals by pull request (index) |
| `v4/pull/<repo>/<pr>` | The pull record of D6, with its error keys |
| `v4/pull-index/<repo>` | Open pull requests (index), for the preview and the sweep |
| `v4/repos` | The repositories of the installation (index), for the sweep |
| `v4/passkey/<github-user-id>` | That user's credentials (task 18), deleted with the tenant on uninstall |
| `v4/challenge/<id>` | One WebAuthn challenge, 5 minutes |

Each value is JSON with `schema`, for example `archfit-app.request.v1`. A record and its index change together in one
`CompareAndSwapAll`.

### Passkey

Relying-party id: the App host. Origin: `https://` plus that host. Attestation `none`. Algorithms ES256, RS256,
Ed25519. `userVerification: required`, and the verifier checks the UV flag. Resident keys preferred. One user handle
per GitHub user id. The sign counter must grow when it is not zero. Verification is `go-webauthn`'s (D9).
