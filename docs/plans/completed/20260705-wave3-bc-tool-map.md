## Book anchors reread

- Ch6 connascence separates static connascence of name, type, meaning, algorithm, and position from dynamic connascence of execution, timing, value, and identity. The book treats connascence as shared-knowledge evidence; strong connascence is acceptable when kept close.
- Ch7 integration strength uses contract, model, functional, symmetric functional, and intrusive coupling. Connascence degrees refine the strength vocabulary, but degrees from different strength levels are not interchangeable.
- Ch8 distance is socio-technical: code proximity, ownership/team boundaries, deployment/runtime boundaries, and vendor/system boundaries all affect how costly a cascade is. Async reduces lifecycle coupling but still represents coupling; missing async evidence must not imply synchronous coupling.
- Ch9 volatility comes primarily from domain role: core subdomains are high volatility; supporting and generic subdomains are low volatility; source control is corroborating and noisy, not the primary classifier.
- Ch10 balance is `max(abs(S-D), 10-V) + 1` on the 1-10 scale. The book warns that numeric coupling is not exact science; confidence and provenance must stay visible.
- Ch11 rebalancing changes strength or distance. Volatility is a domain condition to respond to, not a direct engineer-controlled fix knob.

## Current implementation map

- Book formula and ordinals are centralized in `internal/model/coupling/scorer_book.go`: strength 1/3/8/9/10, distance 2/4/7/9/10, volatility 1/3/6/10, and `max(abs(S-D), 10-V)+1`.
- `coupling_balance` is synthesized from `classified_edges` in `internal/score/score_boundary_coupling.go`; high confidence is capped for tiny samples (`minHighConfidenceScoredEdges=5`, `minHighConfidenceConnectedModules=3`).
- Distance compression is disclosed by `classify.DistanceCompression()` in `internal/classify/distance_structure.go` and surfaced through `classified_edges.distance_compression`.
- Runtime async evidence is report-only at two levels: `internal/engine/assemble.go:buildRuntimeAsync` groups sites by module, and `buildRuntimeAsyncEdges` groups the same sites by source module → runtime target. Neither mutates graph edges, metrics, findings, score, or verdict.
- Clone-only duplicated knowledge is now score-bearing by default under `coupling.duplicated_knowledge: score`: `internal/classify/clone_only.go` scores no-import clone pairs as symmetric strength, and `internal/engine/assemble.go` folds them into `classified_edges` when the policy is `score`.
- Connascence is no longer wholly absent: extractors attach deterministic static hints, classification maps them into `coupling.ConnascenceEvidence`, and `internal/engine/assemble.go:buildConnascenceReport` emits a report-only summary. Dynamic categories remain disclosed as unmeasured.
- Volatility propagation is deterministic and transitive as of Task 2: `computeEffectiveVolatility` raises a strongly coupled source module to high when it depends on a high-effective-volatility target and runs to a fixpoint. This is score-versioned as `bc_score.v6`.
- LLM boundaries remain off-gate: approved labels can influence strength only after review; `analyze --llm` runs after deterministic analysis; `internal/arch_test.go` still forbids internal packages importing `internal/llm`.

## LLM prompt shape to use only when deterministic evidence cannot settle a semantic value

Use one narrow prompt per unresolved value. Do not ask for a whole-repo review when only a label is missing.

Required input:

- The single module pair or edge under review.
- Current deterministic classification and why it abstained.
- Language/tool coverage: Go/TS/Python/Rust extractor, SCIP state, unresolved ratios, clone evidence if relevant.
- Code excerpts around the referenced symbols or imports, plus module public/internal globs.
- Relevant docs/ADR excerpts for subdomain/volatility labels.
- The allowed enum values and a required `unknown` outcome.

Required output:

```yaml
value_kind: strength | subdomain | volatility | runtime_lifecycle_note
candidate: contract | model | functional | symmetric | intrusive | core | supporting | generic | high | medium | low | frozen | unknown
confidence: high | medium | low
evidence_refs: []
rationale: "short, falsifiable reason"
score_effect: "none_until_human_approved"
needs_user_decision: true | false
```

Accept only high-confidence, evidence-cited drafts for human approval. Medium/low drafts stay documentation or backlog input.
