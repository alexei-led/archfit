## 1. System Map

### Entry Point

`main.go` (root, `package main`) is the sole binary entry. It:
- Creates the signal context (`topContext context.Context` — package-level global)
- Sets package-level `runtimeClient ctr.Client` via the `before()` hook
- Wires the `urfave/cli` app with `initializeCLICommands(runtime chaos.Runtime)` where `runtime` is a closure returning `runtimeClient`

### Package Inventory

## 2. Evidence-Backed Findings

### Finding 1: Mocks co-located with production code in `pkg/container`

**Evidence:**
- `pkg/container/mock_Client.go` (27 KB, 26907 bytes) — generated by mockery, `package container`, imports `github.com/stretchr/testify/mock`
- Same for `mock_Executor.go`, `mock_Lifecycle.go`, `mock_Lister.go`, `mock_Netem.go`, `mock_IPTables.go`, `mock_Stressor.go`, `mock_FilterFunc.go`
- `pkg/container/test_helper.go` — also production-package test support
- These are NOT `_test.go` files, so `go list ./pkg/container` and `go build` include testify as a production transitive dependency.

**BC dimension:** Encapsulation — test library (`testify/mock`) bleeds into the production package namespace.

**Severity:** Medium. The `go.mod` lists `testify` already for tests, so no extra dep. But it means `go build` (not just `go test`) must resolve testify, mocks appear in godoc, and the pattern normalizes test scaffolding as first-class production code.

**Fix:** Move mock files to `pkg/container/mocks/` sub-package (Go convention) or use `_test.go` suffix via `package container_test`.

### Finding 2: `pkg/runtime/podman` imports `pkg/runtime/docker` (sibling adapter coupling)

**Evidence:**
- `pkg/runtime/podman/client.go:10`: `"github.com/alexei-led/pumba/pkg/runtime/docker"`
- Uses `docker.NewAPIClient` and `docker.NewFromAPI` as constructor functions
- Package vars: `newAPIClient = docker.NewAPIClient`, `newDelegate = docker.NewFromAPI`
- Podman embeds `ctr.Client` (the Docker delegate) directly in its struct

**BC dimension:** Coupling balance — two sibling adapters (runtime implementations) have a lateral import.

**Balanced Coupling assessment:**
- Strength: FUNCTIONAL — calls exported constructor functions, not internal types
- Distance: PACKAGE — siblings under `pkg/runtime/`, same repo
- Volatility: LOW-MEDIUM — both are generic supporting subdomains (runtime adapters)

By strict BC rule (high strength XOR high distance, or low volatility → balanced): this is BORDERLINE. The distance is package-level (low) and volatility is low, so it avoids being flagged as unbalanced. However, the design creates a hidden constraint: `podman` can never exist without importing `docker`, and future changes to `docker.NewFromAPI` or `docker.NewAPIClient` (e.g., signature changes for a new auth mode) directly break Podman. A shared `pkg/runtime/internal/dockercompat` extraction would sever this dependency while preserving reuse.

### Finding 3: `container.Client` fat interface — builder bypasses narrow per-command interfaces

**Evidence:**
- `pkg/container/client.go`: `Client` embeds `Lister + Lifecycle + Executor + Netem + IPTables + Stressor + Close()`
- Each command defines a narrow local interface (e.g., `killClient` at `pkg/chaos/lifecycle/kill.go:41-44`, `stopClient` at `pkg/chaos/lifecycle/stop.go:22-27`, `pauseClient` at `pkg/chaos/lifecycle/pause.go`)
- BUT `pkg/chaos/cmd/builder.go:CommandFactory` type is `func(client container.Client, gp *chaos.GlobalParams, p P) (chaos.Command, error)` — the generic builder passes the full `container.Client`
- So while commands declare narrow interfaces internally, constructors receive the fat `Client`, defeating Go's implicit interface narrowing at the boundary

**BC dimension:** Coupling balance — contract coupling at the `pkg/chaos` → `pkg/container` boundary is wider than necessary.

**Severity:** Low-Medium. The narrow per-command interfaces still enable unit testing with minimal mocks. The blast radius of adding a new `Client` method is real but contained to adapter packages.

### Finding 4: `architecture_fitness` — `.archfit.yaml` gate is warn-only, no enforcement

**Evidence:**
- `pkg/container/client.go`: `.archfit.yaml` exists at repo root
- `.archfit.yaml` content: one rule `no-forbidden-deps` with `gate: warn` — no `gate: fail` rules
- Comment in file: `# Generated by archfit init — TODO: review and promote gate: warn to gate: fail`
- No `arch_test.go` file anywhere in repo (`find /Users/alexei/Workspace/pumba -name 'arch_test.go'` returns nothing)
- CI (`build.yaml`) runs `make lint` and `make test-coverage` — no explicit architecture gate step
- `mocks/` is classified as `layer: core` in archfit config (should be `test` or `cmd`)

**BC dimension:** Architecture fitness — intended boundaries (layers, forbidden deps) are declared but not enforced by any executable check.

**Severity:** High. The `.archfit.yaml` TODOs are unresolved. Without a failing gate, the adapter coupling and mock placement problems above can spread silently.

### Finding 5: `topContext` and `runtimeClient` as package-level globals in cmd

**Evidence:**
- `cmd/main.go:17-23`: `var (topContext context.Context; runtimeClient ctr.Client)`
- `runtimeClient` is assigned in the `before()` hook via `runtimeClient = client`
- `topContext` is assigned once in `init()` via `handleSignals()`
- All commands capture `topContext` at wiring time via closure; `runtimeClient` is accessed via the `runtime` closure `func() ctr.Client { return runtimeClient }`

**BC dimension:** Encapsulation — global mutable state in the composition root.

**Severity:** Low. This is `package main`, so the global state is scoped to the binary; it cannot leak to library consumers. The `runtime` factory closure pattern already mitigates the worst case. The `runtimeClient` global is a CLI lifecycle pattern, not a design defect. Noted for completeness.

### Finding 6: `mocks/` package — Docker SDK mock of full `APIClient`

**Evidence:**
- `mocks/APIClient.go` — 4000+ line generated mock of `docker.APIClient` (the full Docker SDK client interface, ~100 methods)
- Used only in tests that need a full Docker API surface (e.g., docker/client_test.go)
- The podman package uses a narrower `apiBackend` interface (`pkg/runtime/podman/client.go:21-30`)
- The Docker runtime package already uses focused sub-interfaces (`containerAPI`, `imageAPI`, `systemAPI`)

**BC dimension:** Encapsulation, Testability — the root `mocks/` package is a flat, unstructured test scaffold. Classified as `layer: core` in `.archfit.yaml`, which is a misclassification.

## 5. Top Structural Risks

### Risk 1 (HIGH): No enforced architecture boundary — `.archfit.yaml` gate is `warn` only
`/Users/alexei/Workspace/pumba/.archfit.yaml:13` — `gate: warn`. The module classification (`mocks/` as `core`) is wrong and no rule currently blocks adapter-to-adapter imports. The structural gains from the hexagonal layout are unprotected. Any contributor can add a `pkg/runtime/containerd → pkg/runtime/docker` import and CI will not fail.

### Risk 2 (MEDIUM): `pkg/runtime/podman` tight coupling to `pkg/runtime/docker` internals
`/Users/alexei/Workspace/pumba/pkg/runtime/podman/client.go:10,43-44` — imports `docker.NewAPIClient` and `docker.NewFromAPI`. Podman embeds the Docker delegate (`ctr.Client` embedded field). This is FUNCTIONAL coupling between siblings: any non-backward-compatible change to Docker constructor signatures breaks Podman. The embedding invariant is documented in comments but not enforced by any check.

### Risk 3 (MEDIUM): Mock files in production `pkg/container` package
`/Users/alexei/Workspace/pumba/pkg/container/mock_Client.go` (26,907 bytes) and 7 sibling mock files — not `_test.go` files, not in a sub-package. `testify/mock` is a production transitive dependency. Pattern normalized across the codebase.

### Risk 4 (LOW-MEDIUM): `container.Client` fat interface bleeds through the builder
`/Users/alexei/Workspace/pumba/pkg/chaos/cmd/builder.go:23` — `CommandFactory[P]` receives `container.Client`, not the narrow per-command interface. The narrow interfaces (`killClient`, `stopClient`, etc.) are defined inside each command file but only used for the internal struct field — the constructor still takes `Client`. Adding a new runtime adapter method requires touching every adapter even if no command needs it immediately.

## 6. Recommended Fitness Functions

1. **Import ring gate (CI-fail):** `go test ./... -run TestArchImports` — custom test that uses `golang.org/x/tools/go/packages` to assert `pkg/runtime/*` packages do not import each other (sibling adapter isolation).

2. **No test-lib in production packages (CI-fail):** `grep -r 'testify/mock' $(go list -f '{{.Dir}}' ./...) --include='*.go' | grep -v '_test.go'` — fails if any non-test file imports testify.

3. **Archfit gate promotion:** Promote `.archfit.yaml` `gate: warn` → `gate: fail` for `no-forbidden-deps` and add a `forbidden_import` rule for `pkg/runtime/*` → `pkg/runtime/*` cross-imports.

4. **Interface surface check:** Assert `container.Client` method count does not silently grow — snapshot the method count in a `TestClientInterfaceStability` test that fails on addition.

5. **Layer enforcement:** Reclassify `mocks/` as `layer: test` (or remove from archfit scope) and add a rule that `test`-layer packages cannot be imported by `core`-layer packages.
