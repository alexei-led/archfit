# archfit

Archfit is a Go command-line tool for checking architecture policy against dependency evidence.

## Start here

- User behavior and configuration: `docs/` topic pages. Start with `docs/getting-started.md`.
- System boundaries and change ownership: `docs/architecture.md`.
- Evidence completeness and trust limits: `docs/evidence.md`.
- Build, test, generated contracts, and release: `docs/development.md` and `CONTRIBUTING.md`.
- Superseded plans and design records: `docs/archived/`. Read them only for historical questions.

## Repository rules

- Follow `AGENTS.md` architecture guardrails. Before a cross-module import, run `archfit policy can-import <file> <target>`. Before finishing, run `archfit check --format agent` and follow `next_action`.
- Keep policy, relationship classification, assessment, application workflows, and adapters in their owning layers. Do not move domain decisions into CLI or renderer code.
- Keep evidence completeness separate from metric quality. Missing evidence is not zero. Do not treat waivers or baselines as proof of complete evidence. Follow `docs/evidence.md` when changing promotion or trust rules.
- Supplied coverage is parsed, never generated by Archfit. Keep source-hash freshness checks and producer trust limits intact.
- Keep persisted state baselines separate from `analyze --base`. They answer different questions and use different comparison paths.
- Keep approved label values ahead of LLM suggestions. LLM labels cannot replace approved labels or raise their confidence.
- Keep Go and Rust extraction behind adapters. Core packages must not run tools or import concrete adapters.
- Keep report projection in `internal/application`. It must not import relationship or evidence internals.
- Update the schema and its golden contract when a public configuration or model contract changes. Follow `docs/development.md`.
- Release only through the tag-triggered workflow. Do not create a GitHub release by hand.

## Verification

Run focused package tests for changed behavior. For boundary or contract changes, use the checks in `docs/architecture.md` and `docs/development.md`. Do not regenerate golden files without reviewing the diff.

## Always Do

- **MUST run impact analysis before editing.** Use `impact({target: "symbolName", direction: "upstream"})` (MCP) or `node .gitnexus/run.cjs impact "symbolName" --direction upstream --repo .` (CLI fallback); report callers, processes, and risk. Never substitute grep for graph analysis.
- **MUST analyze graph changes before committing.** Use `detect_changes({scope: "all"})` (MCP) or `node .gitnexus/run.cjs detect-changes --scope all --repo .` (CLI fallback). `partial: true` or `truncated: true` is not a clean check — a zero means unseen, not unaffected; re-run it. For regression review: `detect_changes({scope: "compare", base_ref: "main"})` or `node .gitnexus/run.cjs detect-changes --scope compare --base-ref "main" --repo .`.
- **MUST warn the user** if impact analysis returns HIGH or CRITICAL risk before proceeding with edits.
- **MUST treat `risk: UNKNOWN` as unresolved, not as low.** An empty caller set is not evidence the symbol is unused — it can also mean the callers are not resolvable by the index (plain-object property access, dynamic dispatch, cross-language calls). `impact` pairs `UNKNOWN` with a `riskNote` saying so. Confirm with a text search before treating the symbol as safe to change or delete; do not proceed on the strength of a zero.
- When exploring unfamiliar code, use `query({search_query: "concept"})` to find execution flows instead of grepping. It returns process-grouped results ranked by relevance.
- When you need full context on a specific symbol — callers, callees, which execution flows it participates in — use `context({name: "symbolName"})`.
- For security review, `explain({target: "fileOrSymbol"})` lists taint findings (source→sink flows; needs `analyze --pdg`).

## Never Do

- NEVER edit a function, class, or method before MCP/CLI impact analysis.
- NEVER ignore HIGH or CRITICAL risk warnings from impact analysis, and never read `UNKNOWN` as an all-clear — it means the walk could not answer, which is the one verdict that requires confirming by other means.
- NEVER rename symbols with find-and-replace — use `rename` which understands the call graph.
- NEVER commit before MCP/CLI graph change analysis.
